# 类案检索架构设计

## 整体架构

```
                    ┌──────────────┐
                    │  原始数据源   │
                    │  CSV 16,585  │
                    │  条裁判文书   │
                    └──────┬───────┘
                           │ 过滤：民事案件 + 有实质内容
                           │ 清洗：去重、过滤程序性文书
                           ▼
                    ┌──────────────┐
                    │ PostgreSQL   │
                    │ legal_cases  │  ← 数据源，去重依据
                    └──────┬───────┘
                           │ 全量读取 → 文本清洗
                           │ Dense + Sparse 向量化
                           ▼
                    ┌──────────────┐
                    │ Milvus       │
                    │ case_index   │  ← 检索层，存向量+元数据
                    └──────────────┘
                           │
              ┌────────────┴────────────┐
              │                         │
         guide_agent              legal_qa_agent
         (工作流)                  (问答 Agent)
```

## 一、离线处理阶段

### 1.1 数据源

- 文件：`2021年10月裁判文书数据.csv`
- 总量：16,585 条
- 字段：案号、案件名称、法院、案件类型、案由、全文等

### 1.2 过滤规则

```
保留条件（满足任一即可）：
  a) 案件名称含"判决书"
  b) 全文 > 500 字 且 包含"经审理查明"或"本院认为"等事实分析标记

过滤掉：
  - 纯程序性裁定书（"准许撤诉"等，无案情）
  - 全文 < 300 字
  - 重复数据（相同标题+案由+全文前100字）
```

### 1.3 案由 → Domain 映射

| 关键字 | Domain |
|---|---|
| 劳动、劳务 | `labor_social_security` |
| 交通、事故、机动车 | `traffic_personal_injury` |
| 离婚、婚姻、家庭 | `family_vulnerable_groups` |
| 信用卡、消费、产品 | `consumer_market` |
| 知识产权、作品、商标 | `intellectual_property` |
| 行政、复议 | `administrative_remedies` |
| 其他合同/借贷纠纷 | `contracts_property_housing`（兜底） |

### 1.4 写入 PG

- 表：`legal_cases`
- 断点续传：按 `source = "wenshu_202110"` 过滤已导入的数据，跳过重复
- 批量写入：每批 100 条
- 记录总数：约 2,500-3,000 条

### 1.5 向量化与写入 Milvus

```
PG 读取 → 拼装 _full_text → 删除重建 case_index → 分批 upsert
                                    │
                    不影响 statute_index（独立 collection）
```

**向量化流程：**

```
① BM25 全量训练
   - 输入：所有案例的 _full_text（facts + gist）
   - 分词：jieba 中文分词
   - 输出：词表 + IDF 统计，保存到 models/bm25_case.json

② Dense 向量分批生成
   - 每批 20 条，调用 embedding API（DashScope/Ollama）
   - 1024 维浮点向量
   - 网络抖动自动重试 3 次

③ Sparse 向量预计算
   - 从训练好的 BM25 模型编码所有案例
   - 本地 CPU，毫秒级完成

④ 合并写入 Milvus
   - 每批 20 条，Dense + Sparse 对齐后 upsert
   - 一次写入量约 2,500-3,000 条记录
   - 预估耗时：15-20 分钟
```

### 1.6 存储结构

**PG `legal_cases` 表（数据源）：**

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` | 自增 | 主键 |
| `title` | CSV.案件名称 | |
| `cause` | CSV.案由 | |
| `court` | CSV.法院 | |
| `facts` | CSV.全文 | 清洗后的完整文本 |
| `gist` | 正则提取 | "判决如下"/"裁定如下"之后的关键内容 |
| `domain` | 案由映射 | 12 个领域之一 |
| `source` | 固定值 `wenshu_202110` | 来源标记 |
| `crawled_at` | 导入时间 | 时间戳 |

**Milvus `case_index`（检索层）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR PK | PG id 转字符串 |
| `domain` | VARCHAR | 领域过滤用 |
| `source` | VARCHAR | 来源标记 |
| `title` | VARCHAR(300) | 案件名称 |
| `cause` | VARCHAR(200) | 案由 |
| `court` | VARCHAR(200) | 法院 |
| `text` | VARCHAR(65535) | 案情摘要（facts[:300]） |
| `embedding` | FLOAT_VECTOR(1024) | Dense 向量 |
| `sparse_embedding` | SPARSE_FLOAT_VECTOR | BM25 稀疏向量 |

**Milvus 索引配置：**
- Dense：`IVF_FLAT, COSINE, nlist=128`
- Sparse：`SPARSE_INVERTED_INDEX, IP`

## 二、在线检索阶段

### 2.1 检索管线

```
用户提问："有拖欠工资的类似案例吗？"
         │
         ▼
  ┌─ HyDE（可选）──┐
  │ LLM 生成假设     │  默认关闭（案例检索不用 HyDE，
  │ 案例描述 → 向量化 │  facts+gist 直接向量化更稳定）
  └────────────────┘
         │
         ▼
  ┌─ RRF 混合检索 ──┐
  │                 │
  │  Dense 向量检索  │  embedding 1024d → COSINE 距离
  │                 │  top_k = 15
  │  Sparse 向量检索 │  BM25 → IP 距离
  │                 │  top_k = 15
  │                 │
  │  RRF 融合       │  RRFRanker(k=60) → 15 条
  │                 │
  └────────────────┘
         │
         ▼
  ┌─ Reranker 精排 ─┐
  │ 交叉编码器        │  对 15 条逐一打分
  │                  │  top_k = 5
  └────────────────┘
         │
         ▼
  ┌─ LLM 生成回答 ──┐
  │ 引用案例原文      │  格式：《案件名称》案由、裁判要旨
  │                  │  无匹配时返回兜底提示
  └────────────────┘
```

### 2.2 RRF 融合细节

```
Dense 向量：aembed_query(question) → 1024d → COSINE 搜索
Sparse 向量：encode_queries(question) → BM25 → IP 搜索
                              │
                          RRF 融合
                    rank = 1/(k + position)
                    k = 60（平滑因子）
                              │
                    排序后取 top_k = 15
```

### 2.3 Reranker 精排

- 输入：RRF 输出的 15 条候选结果
- 模型：DashScope 交叉编码器（`gte-rerank`）
- 输出：按相关性重新排序，取 top 5
- 作用：弥补向量检索的精度不足，确保给 LLM 的案例高度相关

### 2.4 LLM 生成回答

- 输入：reranker 精排后的 top 5 案例（标题 + 案情 + 裁判要旨）
- 输出：回答用户问题，引用具体案例
- 无匹配时的兜底：引导用户访问裁判文书网

### 2.5 搜索降级策略

```
RRF 混合检索失败
  → 降级为纯 Dense 向量检索  ← 罕见，API 异常时触发

Milvus 检索返回空
  → 返回兜底提示              ← 数据未就绪或查询异常

Reranker 不可用
  → 直接用 RRF 结果           ← 模型加载失败

PG 回查失败
  → 仅用 Milvus 元数据回复    ← title 等已存 Milvus
```

## 三、与工作流的关系

```
             case_index (Milvus)
                 │
      ┌──────────┴──────────┐
      │                     │
  guide_agent           legal_qa_agent
  (工作流)              (问答 Agent)
      │                     │
  node_retrieve         search_similar_cases
      │                     │
  同源的：                 同源的：
  search_cases_raw()      search_cases_raw()
  + 双路法条融合            + PG 回查
  + Neo4j 图谱             + 单轮 Q&A
```

- 两个 agent 共享 `case_index`，数据一次性导入双方受益
- 工作流从 `case_index` 检索后，还会并行检索法条和 Neo4j，最后融合输出
- 问答 Agent 仅检索 `case_index` + 法条，不涉及工作流的多轮对话
