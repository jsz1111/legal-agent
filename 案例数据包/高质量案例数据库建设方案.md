# 高质量案例数据库建设方案

## 一、建设目标

将 `2021年10月裁判文书数据.csv` 整理为一个通用、可追溯、可直接查询并适合后续向量化的高质量案例数据库。

本方案遵循以下原则：

1. 不修改原始 CSV。
2. 不映射到任何 Agent 的内部领域。
3. 保留司法文书原有的案件类型、审理程序和案由。
4. 删除商业数据网站的 `来源` 字段和正文水印。
5. 保留裁判文书网 `原始链接`。
6. 数据库保存清洗后的完整全文。
7. 向量化只使用精简的案例检索文本，不直接向量化整篇全文。
8. 当前阶段不导入 PostgreSQL、Milvus 或容器，不修改现有 Agent。

## 三、筛选逻辑

### 3.1 元数据筛选

第一批案例采用高精度条件：

```text
案件类型 = 民事案件

审理程序属于：
- 民事一审
- 民事二审
- 民事审判监督

案件名称包含：
- 判决书

案由：
- 不为空
- 不等于“民事”
- 不等于“其他案由”

原始链接：
- 不为空
```

不进行 Agent 领域映射，直接使用裁判数据中的原始案由分组。

### 3.2 全文筛选

清洗后全文必须满足：

```text
全文长度：1200—8000 字
包含：本院认为
包含：判决如下
案件内容章节不少于 80 字
法院说理章节不少于 80 字
裁判结果不少于 20 字
```

裁判结果存在以下程序性内容时排除：

```text
准许撤回起诉
按撤诉处理
不予受理
驳回起诉
移送管辖
管辖权异议
终结本次执行程序
终结执行
中止诉讼
```

### 3.3 去重和抽样

去重优先级：

```text
案号
→ 原始链接
→ 全文哈希
```

每个原始案由最多保留 50 条，并在同一案由内跨地区均衡抽取，避免结果集中在同一家法院或同一地区。

案由不足 50 条时保留全部合格案例，不使用低质量文书补足数量。

## 四、文本清洗

仅对通过筛选的案例进行深度清洗：

1. 去除 UTF-8 BOM、零宽字符和 HTML 空白实体。
2. 修复中文字符之间的异常空格。
3. 合并多余空格、换行和制表符。
4. 删除 `文书内容` 等固定前缀。
5. 删除“马克数据网”“百度搜索”“关注公众号”等商业尾注。
6. 不改变案号、金额、日期、法院观点和裁判结果。
7. 原始 CSV 保持不变，清洗结果写入独立数据包。

## 五、案例数据结构

处理后保留原始数据的全部有效元数据，仅删除 `来源`，并增加检索和质量控制字段。

| 字段 | 说明 |
|---|---|
| `case_id` | 根据案号、原始链接和正文生成的稳定唯一 ID |
| `原始链接` | 中国裁判文书网原始链接 |
| `案号` | 原始案号 |
| `案件名称` | 原始案件名称 |
| `法院` | 审理法院 |
| `所属地区` | 原始地区元数据 |
| `案件类型` | 原始案件类型 |
| `案件类型编码` | 原始类型编码 |
| `审理程序` | 一审、二审或审判监督 |
| `裁判日期` | 裁判日期 |
| `公开日期` | 公开日期 |
| `当事人` | 原始当事人字段 |
| `案由` | 原始案由，不做 Agent 映射 |
| `法律依据` | 原始法律依据字段 |
| `全文` | 去除水印并规范格式后的完整文书 |
| `全文字数` | 清洗后全文长度 |
| `retrieval_text` | 用于后续向量化的案例检索文本 |
| `筛选标签` | 当前案例通过的质量规则 |

明确不保存：

```text
来源
domain
agent_domain
```

## 六、检索文本设计

`retrieval_text` 与完整全文分开保存。

每条检索文本由以下内容组成：

```text
案件名称
案由
案件内容摘录
法院认为
裁判结果
```

当前实际长度为 443—754 字，平均约 627 字。

示例结构：

```text
案件名称：某某劳动争议民事判决书
案由：劳动争议
案件内容：诉讼请求、关键事实和主要证据……
法院认为：法院对争议事实和法律责任的认定……
裁判结果：支持、部分支持或驳回的具体结果……
```

检索文本使用裁判文书原文摘录和规则截取，不调用大模型生成，不改变案件事实。

## 八、后续向量化方案

### 8.1 向量化对象

不向量化完整全文，只向量化 `retrieval_text`：

```text
完整全文 → SQLite/PostgreSQL 保存，用于用户查看和事实追溯
retrieval_text → Embedding，用于语义召回
元数据 → 用于过滤、展示和结果排序
```

第一版采用一案一个案例检索文本：

```text
一个案例
→ 一个 Dense 向量
→ 一个 BM25 Sparse 向量
```

不进行递归切分，不把一篇裁判文书拆成大量无上下文片段。

### 8.2 批量处理

建议每批处理 16—32 条 `retrieval_text`，避免逐条调用 Embedding 模型。

当前项目默认使用本地 Ollama `bge-large`，本地向量化不产生远程 API 计费，但仍应控制输入长度，避免模型截断和无关文字稀释语义。

### 8.3 Milvus 元数据

后续 Milvus 可以保存检索所需的完整元数据：

```text
case_id
original_url
case_number
case_name
court
region
case_type
case_type_code
procedure
judgment_date
publication_date
parties
cause
legal_basis
full_text_length
retrieval_text
embedding
sparse_embedding
```

不保存商业 `来源` 字段，也不新增 Agent 领域字段。

完整全文可以继续保存在 SQLite 或后续 PostgreSQL 中；Milvus 命中后可直接返回元数据和 `retrieval_text`，只有用户主动查看全文时才按 `case_id` 查询完整文书。

## 九、后续检索流程

建议采用通用检索管线：

```text
用户问题
→ 查询文本向量化
→ Dense 语义检索
→ BM25 关键词检索
→ RRF 融合
→ reranker 精排
→ 选取最相关的 1—2 个案例
→ 大模型整理相似点、差异点、法院观点和裁判结果
```

元数据可按用户查询需要参与过滤：

```text
案由
案件类型
审理程序
法院
地区
裁判日期
```

检索阶段不强制进行 Agent 领域过滤，避免因领域映射错误导致相关案例无法召回。

## 十、用户展示方式

默认只向用户展示精简结果：

```text
案件名称和案号
法院和裁判日期
核心案情
相似点和差异点
法院观点
裁判结果
原始链接
```

单个案例展示约 150—300 字，一次展示 1—2 条。用户需要进一步核对时，再从数据库读取清洗后的完整全文。

案号、法院、裁判日期、裁判结果和原始链接必须来自数据库字段，不能由大模型自行编造。

## 十一、质量控制

当前已完成的自动校验：

1. CSV、JSONL 和 SQLite 均为 752 条。
2. SQLite `PRAGMA integrity_check` 返回 `ok`。
3. case_id 和案号均无重复。
4. 必需元数据无缺失。
5. 原始链接全部为裁判文书网链接。
6. 商业品牌水印清零。
7. `retrieval_text` 长度处于 443—754 字。
8. 筛选、清洗、SQLite生成相关测试共 6 项，全部通过。

仍需完成的质量工作：

1. 按高频和低频案由分层人工抽查。
2. 建立 30—50 条查询到案例的人工相关性评测集。
3. 向量化后验证 Top 5 召回率和 reranker 排序质量。
4. 对法律依据缺失、文本截取不完整的个别案例进行人工标记。

## 十二、当前边界

本数据包当前是可直接查询、可继续向量化的通用案例数据库，但尚未：

```text
导入 PostgreSQL
写入 Milvus
接入任何 Agent
调用大模型逐案总结
完成人工逐案法律审核
```

后续应先完成抽样人工审核，再进行批量向量化和检索效果评测。
