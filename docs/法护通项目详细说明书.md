## 2. 项目定位

法护通是一个面向普通市民和企业用户的法律信息与维权行动辅助平台。它不是单纯的聊天机器人，而是把以下能力组成一套连续流程：

- 判断用户是在问一般法律知识，还是在处理自己的具体纠纷；
- 对具体纠纷建立独立案件状态，跨多轮保存事实、证据、风险和行动方案；
- 从法条、案例、图谱、渠道、官方模板和法律年鉴中检索可核验信息；
- 将用户口语描述整理成法律问题、原子事实和待证明目标；
- 支持图片、PDF、DOCX、TXT 等材料的初步解析和证据用途梳理；
- 输出法律依据、类案参考、渠道建议、证据缺口、优劣势和行动清单；
- 将最终方案导出为可编辑 Word，并提供相关官方空白模板。

项目对外边界是“法律信息与行动辅助”。系统不能替代律师、法院、仲裁机构、行政机关或其他有权机构作出个案结论，也不能确定证据的真实性、合法性、可采性和最终证明力。

# 第一部分：知识库系统

## 5. 知识库不是一个库，而是八类知识资产

| 知识资产 | 主存储 | 辅助索引 | 用途 | 能否直接作为法律依据 |
| --- | --- | --- | --- | --- |
| 法律与法条 | PostgreSQL `laws`、`articles` | Milvus `statute_index`、Neo4j | 法律规定、权利义务、法律后果 | 必须回链法律名称、条号和原文 |
| 类案 | PostgreSQL `legal_cases` | Milvus `case_index`、Neo4j | 相似事实和裁判思路参考 | 不能替代现行法和个案判断 |
| 法律关系图谱 | Neo4j | PostgreSQL ID 回链 | 领域—法律—法条—案例—渠道关系 | 只作导航和辅助推理 |
| 维权渠道 | PostgreSQL `channels` | Neo4j | 电话、网址、办理材料和地域渠道 | 可展示，但应关注核验日期和地域 |
| 权威来源与追问依据 | PostgreSQL 三张来源表 | Milvus `authority_basis_index` | 给动态追问和证据目标提供来源说明 | 只有审核通过且精确定位后才可正式引用 |
| 专业文档 | 设计上为 MinIO + Milvus `knowledge_docs` | Milvus | 合同、文书和专业资料问答 | 取决于文档来源与授权状态 |
| 法律统计 | 独立 PostgreSQL `legal_statistics` schema | 目录检索 + 受限 NL2SQL | 年鉴数量、趋势、比例和图表 | 仅为统计资料，不是法律依据 |
| 用户长期记忆 | Milvus `agent_long_term_memory` | 语义检索 | 跨会话记住地区、案件摘要等 | 不是公共知识，也不能覆盖本轮陈述 |

此外还要区分两种证据数据：

- **公共证据规则库**：证明目标、建议材料、替代材料、评估维度和来源映射；
- **案件证据库存**：某个用户实际上传或声称持有的材料及其评估，只属于该案件状态。

## 6. 数据来源与分层治理

### 6.1 正式来源 `data/sources/formal`

该目录按日期和批次保存国家法律法规数据库、政府部门、法院等公开来源的下载产物与报告。代码通过 `download_report.json`、本地文件路径和 SHA-256 建立来源登记。

当前来源治理字段包括：发布机关、官方页面、官方文件地址、发布日期、生效日期、历史版本、本地路径、文件哈希、内容类型、审核状态和生产状态。

仓库中仍存在 `QUARANTINED` 或 `integrity_verified_pending_legal_review` 状态。这表示文件完整性可核对，但法律内容未完成正式审核，不能因为已经下载就自动视为可生产引用。

### 6.2 实践来源 `data/sources/practical`

主要是办事指南、行政服务说明、仲裁申请指南和公开维权手册。它们适合回答“去哪里办、准备什么、怎样提交”，但必须保留：

- 发布机关；
- 适用地域；
- 发布时间或核验时间；
- 是否只是办事说明而非法律规范；
- 是否存在过期或地方差异。

### 6.3 案例来源

案例数据来自三条线：

1. `cail2019_scm`：刑事案例语料；
2. 正式来源中的 concrete 案例：劳动、消费等具体样例；
3. `case_pilot`：从 16,585 条候选中按案由、正文长度、来源链接和质量条件筛选出 752 条，覆盖 123 个案由。

`case_pilot/manifest.json` 当前仍标记 `database_imported=false`、`vectorized=false`。这描述的是该离线包自身的流水线标记，不应与历史运行实例中已经存在的案例数混为一谈。

### 6.4 法律统计来源

`data/sources/legal_statistics` 是中国法律年鉴 2019—2021 的离线统计包，统计年份覆盖 2015—2020。清单记录：

| 项目 | 数量 |
| --- | ---: |
| 工作簿/数据集 | 193 |
| 行记录 | 3,044 |
| 展平统计事实 | 11,612 |
| 原始审计单元格 | 23,573 |

这些数据保留原工作簿、工作表、行列位置、文件哈希、质量标记和统计口径，供查询结果回溯。

### 6.5 官方文书模板

`resources/legal_document_templates/manifest.json` 登记了最高人民法院、司法部、中华全国律师协会 2025 年示范文本中的 8 类起诉状空白模板：离婚、买卖合同、房屋买卖、民间借贷、房屋租赁、劳动争议、交通事故、著作权。

每个模板保存案由、适用领域、关键词、诉讼请求栏目、事实栏目、证据栏目、来源页码、官方来源和空白 PDF 哈希。模板只能用于栏目提示和材料准备参考，不能推导“所有案件都必须提交这些材料”。

## 7. PostgreSQL 主数据模型

### 7.1 业务库

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `laws` | title、category、authority、domain、effective_from、file_path | 法律文件元数据 |
| `articles` | law_id、article_no、content | 法条正文 |
| `legal_cases` | case_id、案号、案由、法院、事实、要旨、全文、检索文本、来源链接 | 类案主数据 |
| `law_cases` | law_id、case_id | 法律与案例关联 |
| `channels` | domain、region_code、电话、网址、材料、来源、核验日、状态 | 维权渠道目录 |
| `authority_sources` | source_key、issuer、source_type、authority_level、official_url、status | 跨版本来源登记 |

| `followup_rule_citations` | rule_id、rule_type、source_version_id、locator、excerpt、mapping_status | 追问规则与来源映射 |

PostgreSQL 是结构化事实和来源信息的主数据。Milvus 命中后需要回查 PostgreSQL 补齐法律名称、案例详情和来源字段。

### 7.2 法律统计库

统计库使用同一 PostgreSQL 服务中的独立数据库和只读账号，主要表为：

- `datasets`：每张原始统计表的来源、年度、机构、主题和哈希；
- `records`：按原表行重建的 JSON 记录；
- `facts`：每个数值单元格展平后的长表；
- `cells`：原始单元格审计表；
- `category_mappings`：跨年度类别名称映射。

## 8. Milvus 索引设计

### 8.1 `statute_index`

- 主键：`law_id + article_no`；
- 元数据：领域、法律 ID、条号、法条正文；
- 向量：1024 维 Dense 向量；
- 稀疏向量：使用 jieba 分词训练的 BM25；
- 索引：Dense `IVF_FLAT/COSINE`，Sparse `SPARSE_INVERTED_INDEX/IP`；
- 查询：Dense 与 Sparse 并行，使用 RRF 融合，再调用 `qwen3-rerank` 精排；
- 领域过滤时额外保留民法典作为跨领域基础私法候选。

### 8.2 `case_index`

- 保存案例 ID、领域、来源、展示摘要、Dense 和 BM25 Sparse 向量；
- 查询时可组合原始问题向量、HyDE 假设案例向量和 BM25；
- 命中后回查 PostgreSQL 获取标题、案由、法院、案号、日期、要旨和来源链接；
- 对通用民事案例按案由和领域标记做二次过滤，防止字面相似但法律关系不同的案例混入。

主初始化脚本 `init_milvus_indexes.py` 对案例默认只按每个领域抽取 2 条样本，因此它适合基础验证，不等同于完整案例库构建。完整案例索引还依赖 `import_case_pilot.py`、`update_milvus_incremental.py` 等专项脚本。

### 8.3 其他集合

| 集合 | 内容 | 特点 |
| --- | --- | --- |
| `legal_term_index` | 从法条和领域中抽取的法律概念 | 用于口语—法律术语映射；构建脚本还会写入 Neo4j `LegalConcept` |
| `authority_basis_index` | 追问规则、来源、定位和解释文本 | HNSW/COSINE；只辅助召回，不直接决定工作流 |
| `knowledge_docs` | 专业文档分块 | 代码支持文档名、类型、页码、块号和文本，但当前主初始化流程没有稳定装载器 |
| `agent_long_term_memory` | 用户画像和案件摘要 | 按用户 namespace 隔离，支持语义搜索、覆盖写和删除 |

所有集合都依赖 Embedding 输出维度与集合维度一致。当前多个集合固定为 1024 维，切换 Embedding 模型时必须先验证维度，必要时重建集合。

## 9. Neo4j 法律图谱

图谱初始化脚本从 PostgreSQL读取数据，创建：

```text
(Law)-[:HAS_ARTICLE]->(Article)
(LegalCase)-[:CITES]->(Law)
(Law)-[:APPLIES_TO]->(Domain)
(Channel)-[:HANDLES]->(Domain)
(LegalConcept)-[:BELONGS_TO]->(Domain)  # 概念构建脚本扩展
```

图谱用于发现“某领域有哪些法律、有哪些办理渠道、法律与案例如何关联”。法律问答中的图谱检索流程是：实体提取 → LLM 生成 Cypher → 执行，失败最多重试 2 次 → LLM 整理结果。

图谱查询结果不是法律原文。涉及条号和正文时仍需回到 PostgreSQL/Milvus 法条链路。生产部署还应对生成的 Cypher 增加只读语法白名单和资源限制；当前代码主要依靠提示词和数据库权限约束。

## 10. 法条检索链路

```text
用户问题
  → 法律术语改写
  → 可选 HyDE 生成“假设法条”
  → Dense 向量 + BM25 稀疏向量
  → Milvus RRF 混合召回
  → Qwen Reranker 精排
  → PostgreSQL 补齐法律名称
  → 组织“核心法条/参考法条”上下文
  → LLM 基于上下文回答
  → 幻觉接地检查
  → UI 展示法条原文和来源信息
```

降级策略：

- RRF 失败时退化为纯 Dense 检索；
- Milvus 无结果且有数据库会话时，用 PostgreSQL `ILIKE` 做法条正文关键词兜底；
- Reranker 不可用时保留原向量排序；
- 幻觉检查调用失败时目前采取放行策略，这一点需要通过日志、回归测试和生产监控补强。

维权 Agent 的完整检索还会同时执行“领域过滤法条”和“全库法条”，RRF 融合后统一精排，以降低领域识别错误导致零召回的风险。

## 11. 类案检索链路

```text
案件事实与争点
  → 构造语义查询和法律关键词查询
  → 原问题 Dense + 可选 HyDE Dense + BM25
  → RRF 融合和精排
  → PostgreSQL 回查完整案例
  → 案由、领域、主题和数据质量二次过滤
  → 输出类案事实、裁判要旨和差异提示
```

如果没有合格类案，系统返回中国裁判文书网入口和搜索建议，而不是虚构案例。类案只提供参考，最终方案必须以现行法律和本案事实为主。

## 12. 法律统计 NL2SQL 与 ChatBI

统计链路与业务库隔离：

1. jieba 分词、短语和年份提取；
2. 从真实 `datasets/facts` 中确定性召回候选表、维度和指标；
3. LLM 只基于真实目录生成一条 SQL；
4. 白名单校验 SQL；
5. 在只读事务中执行，并设置 10 秒超时；
6. 确定性格式化数字和趋势；
7. 生成结构化行、来源、图表建议和摘要；
8. 把上次 SQL 和结果保存在 Redis，支持“再加一个指标”等连续追问。

SQL 安全约束包括：只允许单条 `SELECT`、必须使用 `legal_statistics` 全限定表、只允许四张白名单表、禁止子查询/CTE/UNION/写操作/系统对象/危险函数/聚合函数、最多返回 100 行，并在数据库事务层再次设置只读。

系统禁止直接聚合 `facts` 单元格，避免把“合计”行和分类明细重复相加。趋势与增减由返回行确定性计算；LLM 生成的摘要若出现数据集中不存在的数字，会回退到规则摘要。

## 13. 权威来源与可追溯性

追问依据采用三层模型：

```text
AuthoritySource（稳定来源）
       ↓
AuthorityVersion（具体版本、文件与哈希）
       ↓
FollowupRuleCitation（规则、定位、摘录与派生说明）
```

当前离线导出包含 18 个来源和 116 条规则引用。状态分布为：

- 来源：17 个 `integrity_verified_pending_legal_review`，1 个 `system_only`；
- 映射：75 个 `needs_pinpoint`、35 个 `source_located`、6 个 `system_only`。

这说明来源治理框架已经建立，但大部分内容仍处于“完整性已验证、法律审核或精确定位待完成”的阶段。面向生产的正式引用至少应满足：来源 active、版本有效、法律审核通过、条文/页码精确定位、哈希一致。

## 14. 附件与证据知识处理

### 14.1 文档附件

`upload-document` 支持 PDF、DOCX、TXT，最大 10 MB：

- PDF 最多读取前 30 页；
- 提取文字最多 8,000 字；
- 生成 SHA-256；
- 将文件名、来源形式、哈希和提取文字组成“证据补充块”；
- 后端默认不保留原文件；
- 扫描 PDF 没有文字时提示改传清晰图片或手动说明。

### 14.2 图片附件

图片支持 JPG、PNG、WEBP、GIF、BMP。系统校验真实格式、文件大小、像素数和完整性，计算原图 SHA-256，再把当前案件领域、争点、证据清单和最近追问加入视觉提示。

视觉输出结构包括：证据类型、清晰度、可见文字、关键事实、可能证明事项、局限和待核验内容。提示词要求对身份证号、银行卡号、手机号、住址等敏感信息做非必要部分遮盖。图片副本默认处理后删除，只有明确启用保留配置时才留存。

### 14.3 证据评估模型

单份材料会记录：

- 是否上传、用户称持有、明确缺失或存在冲突；
- 原件、原始电子文件、平台导出、截图或复制件等来源形式；
- 完整性、主体可见性、时间可见性、取得方式和本案特异性；
- 交易、付款、沟通、损失、程序等证明角色；
- 原文摘录、材料间冲突、限制和待核验项。

系统把规则转成 `ProofTarget`，再用 `EvidenceLink` 连接材料和待证事实，最终形成 `preliminarily_covered`、`partially_covered`、`known_missing`、`conflicted`、`unresolved` 等工作流覆盖状态。

这些状态表示“生成行动方案所需的信息准备度”，不是司法意义上的证据效力结论。

## 18. 会话模式与路由原则

请求支持三种模式：

- `case`：直接进入案件维权状态机；
- `qa`：直接进入独立法律问答；
- `auto`：仅在尚未分类的首轮交给 Supervisor 判断。

服务端会把模式保存到 Redis。同一个 `user_id + session_id` 一旦进入问答或案件模式，后续不会静默切换。只要检测到已有 GuideState，该会话优先判定为案件模式；旧版已经有问答历史的会话会回填为问答模式。

这个隔离解决了两个问题：

1. 一般法律知识问答不会误写入案件事实；
2. 已经建立的案件不会因为用户后续问了一个法律概念就丢失状态。

## 19. Supervisor 工作方式

Supervisor 使用 LangChain `create_agent`，拥有：

- `call_guide_agent`；
- `call_legal_qa_agent`；
- 三个预留 Worker；
- `save_memory`、`search_memory`。

它的系统规则要求自己不直接回答法律问题，而是将用户原始输入交给专项 Worker，并完整透传 Worker 回复。具体事件、已经发生在用户身上的纠纷和明确维权诉求进入 Guide；法律概念、法条含义、制度流程和统计问题进入 Legal QA。意图不明确时先询问用户想了解规定还是处理自己的纠纷。

Supervisor 的短期记忆由 Redis Checkpointer 保存。消息达到约 4,000 token 或 6 条时触发摘要，并保留最近 6 条消息。长期记忆使用 Milvus，按 `users/{user_id}/memories` 隔离。

为了避免模型把长期记忆伪装成本轮陈述，Worker 工具只把用户原始消息传给 Guide，历史记忆作为独立上下文传入。Guide 还会自己再做一次相关记忆检索。

## 20. 法律问答 Agent

### 20.1 六个工具

| 工具 | 适用问题 | 底层链路 |
| --- | --- | --- |
| `search_statute` | 法条、权利义务、法律后果 | 改写 + HyDE + Dense/BM25/RRF + PG 回链 + 接地校验 |
| `search_similar_cases` | 同类纠纷、裁判思路 | Dense/HyDE/BM25 + PG 详情 + 质量过滤 |
| `search_legal_graph` | 领域法律、法律关系、渠道 | 实体抽取 + NL2Cypher + Neo4j |
| `search_channels` | 电话、网址、办理方向 | PostgreSQL 确定性查询、地域和优先级排序 |
| `search_legal_docs` | 合同、专业文书或知识文档 | `knowledge_docs` 向量检索 + 页码引用 |
| `search_legal_statistics` | 数量、趋势、比例、跨年对比 | 独立统计库 + 安全 NL2SQL + ChatBI |

### 20.2 单轮执行

每轮问答会创建独立的 Milvus Client，避免空闲连接失效和并发共享问题。Agent 调用工具后，系统提取本轮检索轨迹，形成统一调试面板数据。

法条回答如果没有把召回的法条正文写入输出，Worker 会确定性追加最多 3 条“检索法条原文”。统计回答则强制透传 ChatBI 的确定性答案，防止外层 Agent 二次改写数字或补造原因。

问答历史保存在 Redis，最多保留最近 6 条消息，默认受 `REDIS_SESSION_TTL` 控制。统计上下文单独保存上次 SQL，以支持连续对比。

## 21. Guide Agent 的状态模型

GuideState 不是普通聊天记录，而是按职责分组的案件黑板：

| 子状态 | 主要内容 |
| --- | --- |
| `case` | 轮次、会话、案件 ID、案件代次、边界判断、用户上下文、领域、地区和时间 |
| `issues` | 已确认/未匹配问题、术语映射、案件框架、场景置信度 |
| `facts` | 原子事实、可写入文书的事实、事实台账和不利事实 |
| `followup` | 场景分析、已问/待问问题、动态计划、决策轨迹、追问依据 |
| `evidence` | 材料评估、证明目标、证据关联、覆盖状态和版本号 |
| `retrieval` | 法条、类案、渠道、图谱和检索快照 |
| `control` | 是否强制收敛、追问轮次、低信息回答计数和置信度 |
| `safety` | 紧急风险、人身安全暂停、诈骗止损和时效警告 |
| `output` | 最终方案、案件分析包、争点图、法律依据包和审校状态 |
| `strategy` | 策略计划、版本、阶段和校验结果 |

状态同时保留旧版平铺字段兼容层，旧 Redis JSON 会在加载时自动迁移。这样既减少 LangGraph 顶层通道数量，也避免历史会话升级后无法读取。

## 22. GuideGraph 九节点工作流

```text
prepare_turn → check_urgency → extract_issues
                                      │
                       无法归类 ──────┴→ clarify → END
                                      │
                                      ▼
                              assess_retrieve
                                 │         │
                         仍需信息│         │信息足够/用户要求
                                 ▼         ▼
                           ask_followup   conclude
                                 │         │
                                END    save_record → END

有待回答问题时：prepare_turn → check_urgency → parse_details
                                             ├→ extract_issues
                                             ├→ assess_retrieve
                                             └→ END（用户反问，保留待答问题）
```

### 22.1 `prepare_turn`

- 首轮加载 PostgreSQL 历史咨询和相关长期记忆；
- 每轮只在此处推进轮次；
- 识别“现在生成方案”“继续补充”等流程控制意图；
- 防止把纯控制语句当成案件事实。

### 22.2 `check_urgency`

- 每轮执行，而不是只检查首轮；
- 对现实人身危险、暴力、拘留、诈骗止付、时效紧迫等进行三级分类；
- CRITICAL 时先给报警、止付、就医或法律援助提示，并中断普通追问；
- 安全暂停可恢复，用户确认安全后继续原案件。

### 22.3 `extract_issues`

- 读取最近对话和本轮附件块；
- 把口语叙述标准化为 13 个领域之一；
- 抽取法律问题、地区、时间和原子事实；
- 每条事实记录来源文本、轮次、状态、确定性、是否可写入文书和证据状态；
- 新事实与旧事实通过 reducer 合并，支持补充、更正、否认和冲突记录。

### 22.4 `clarify`

当领域和法律问题均无法确定时，以低负担问题让用户说明“发生了什么、希望解决什么”。默认最多 2 轮，仍然模糊时进入保守降级，避免无限盘问。

### 22.5 `assess_retrieve`

这是工作流的决策中心，内部包含多步：

1. 场景再判断：识别同一领域下更具体的法律关系；
2. 场景置信度不足时，生成单独的辨别选项；
3. 更新证据材料、证明目标、覆盖状态和证据清单版本；
4. 计算规则式置信度；
5. 评估责任主体、请求范围、时效、管辖、程序、证据和安全等决策维度；
6. 追问阶段执行轻量法条与权威依据检索，不检索类案；
7. 事实足够或用户要求收敛时执行完整法条、类案、图谱和渠道检索；
8. 生成下一轮动态追问计划，或直接进入结论。

### 22.6 `ask_followup`

正常情况下输出 2—5 个混合表单问题，支持短文本、长文本、单选和多选。固定领域目录先覆盖必问事实，随后由动态规划器针对未解决的法律决策维度补问。

每个候选问题会评估：

- 对责任、请求、时效、管辖、程序、证据或安全决策的信息增益；
- 用户回答负担；
- 是否已经回答、否认、不知道或重复；
- 是否有法条、权威来源或案件事实作为询问依据；
- 是否达到最小追问价值阈值。

事实基本收敛后，节点会集中展示证据准备清单，而不是继续零散追问材料。

### 22.7 `parse_details`

- 解析结构化表单回答或普通聊天回答；
- 只处理本轮用户明确提供的信息；
- 合并事实、证据、地区和时间；
- 检查与既有事实或材料的冲突；
- 用户反问时先回答反问，再恢复原待答问题，不消耗正常追问轮次；
- 纯“给方案”指令直接转入收敛，不送入事实抽取。

### 22.8 `conclude`

结论节点不是一次简单 Prompt，而是一条分析、策略和审校子流水线：

```text
冻结案件事实
  → 构建 case_analysis_packet
  → 识别 issue_map（争点图）
  → 按争点补充法条检索
  → 构建 legal_basis_packet
  → 逐争点法律适用分析
  → 事实/法条接地校验
  → 并行执行策略综合 + 用户处境审视
  → 对方/机关/平台/执行四视角压力测试
  → 生成方案初稿
  → 确定性格式检查
  → 必要时批判与最多两轮修订
  → 清理未召回法条引用
  → 补齐必须栏目并形成最终方案
```

最终输出重点包括：案件情况、当前结论、法律依据、争点与要件分析、事实矛盾、证据作用和缺口、可选路径比较、最优程序路径、反方压力测试、优劣势、优先行动清单和后续补充入口。

系统会删除或纠正不在本轮召回上下文中的法律名称/条号，并确定性补上已召回法条原文。它不输出胜率百分比，也会把未核实事实改写为条件式判断。

### 22.9 `save_record`

将用户、会话、领域和问题摘要保存为 PostgreSQL 咨询记录。保存失败只记日志，不吞掉已经生成的用户方案。结论节点还会把用户地区和案件摘要写入 Milvus 长期记忆。

## 23. 收敛、置信度与追问上限

### 23.1 置信度

置信度为确定性规则评分，不额外调用模型：

- 证据准备度：40%；
- 事实清晰度：30%，由领域、地区和时间组成；
- 权责清晰度：30%，由已确认法律问题数量组成。

默认阈值为 HIGH ≥ 0.65，MEDIUM ≥ 0.50，否则 LOW。该分数控制方案表达强度，不代表胜诉概率或证据证明力。

### 23.2 决策充分性

系统按法律决策维度判断是否足够生成明确方案：责任主体、请求范围、时效、安全属于阻塞型维度；管辖、程序和证据缺口通常属于建议型维度。

结果分为：

- `conclude_definitive`：最低决策维度已覆盖；
- `conclude_conditional`：可以给条件式方案，但仍有缺口；
- `ask`：仍有高价值问题值得询问。

### 23.3 体验与硬限制

默认配置包括：澄清最多 2 轮、事实追问最多 3 轮、证据追问最多 3 轮、普通追问硬上限 6 轮、用户明确继续后绝对上限 8 轮、软体验上限 3 轮、总轮次异常保险 20 轮。连续低信息回答或连续反问也会触发收敛或低负担选项。

用户在任何阶段都可要求“按现有信息生成方案”。系统必须给出条件式建议，并把未知信息写成风险或待核验项，而不能继续强制追问。

## 24. 案件边界与多案件隔离

每个案件有独立 `case_id` 和 `case_generation`。当用户在同一会话中突然描述另一件事时，系统判断：

- `CONTINUE`：继续当前案件；
- `NEW`：归档旧 GuideState，创建新案件状态；
- `UNCERTAIN`：先让用户确认是否为新案件。

边界决策会写入审计记录。证据提交和“重新生成方案”使用结构化 action，并可带 `target_case_id`；如果客户端指定的案件 ID 或证据清单版本已经过期，接口返回 409，防止材料串案。

## 25. 文书与最终产物

用户请求“生成文书”时，当前实现实际导出的是 `node_conclude` 已生成的最终行动方案 Word 版，而不是再次让模型自由代写一份新诉状。

流程为：

1. 读取 `latest_plan_text`；
2. 生成可编辑 DOCX；
3. 匹配相关官方空白模板；
4. 将文件字节和元数据暂存 Redis；
5. 返回随机 32 位文书 ID 和下载 URL；
6. 默认 24 小时后过期。

这样可避免“用户上传的证据材料里出现‘民事起诉状’字样”被误识别成文书命令。附件注入块带有固定标记和 SHA-256，路由会先识别证据注入，再判断文书请求。

| DELETE | `/api/v1/chat/conversations/{session_id}` | 删除会话状态、检查点、临时文书和案件长期记忆 |
| GET | `/api/v1/chat/document-templates` | 官方模板目录 |
| GET | `/api/v1/chat/document-templates/{id}/official` | 下载官方空白 PDF |
| GET | `/api/v1/chat/documents/{id}` | 下载短期 DOCX |
| GET | `/health` | 应用存活 |
| GET | `/health/deps` | PostgreSQL、Redis、MinIO、Milvus、Neo4j 依赖检查 |

对话请求主要字段：

```json
{
  "user_id": "anonymous-user",
  "session_id": "conversation-id",
  "message": "公司拖欠我三个月工资。",
  "mode": "case",
  "action": "message",
  "target_case_id": "",
  "regenerate_solution": false,
  "evidence_requirement_ids": []
}
```

SSE 事件包括 `progress`、`token`、`done` 和 `error`。进度只公开“风险检查、事实整理、检索、证据评估、方案生成”等业务阶段，不暴露模型内部思维链。

## 27. 前端交互

网页端是单页 React 应用，主要能力包括：

- 法律问答与案件维权双入口；
- 浏览器本地生成匿名用户 ID；
- 问答和案件分别保存活跃会话；
- 多会话历史保存在 `localStorage`；
- 不同会话可并发运行，同一会话由前端保持串行；
- SSE 进度面板；
- 动态追问表单；
- 证据中心和多文件上传；
- 检索/调试侧栏；
- 法律统计图表；
- 官方模板和 Word 下载；
- 会话删除。

浏览器本地记录主要用于交互恢复，服务端 Redis 才是案件模式和 GuideState 的权威状态来源。

## 30. 当前主要限制与风险

1. **运行实例未实时盘点**：本次审阅时 Docker 未运行，数据库和 Milvus 实际数量需要重新核验。
2. **法律审核未闭环**：多数权威来源仍是待法律审核或待精确定位状态。
3. **专业文档库未稳定装载**：`knowledge_docs` 查询代码存在，但主建库脚本没有完整上传、切块、版本和删除链路。
4. **案例覆盖不均衡**：不同领域的类案数量和质量差异大；无结果时必须明确降级。
5. **案例初始化容易被误解**：基础 Milvus 脚本只抽样案例，不能替代完整案例导入。
6. **Embedding 维度固定**：多个集合写死 1024 维，换模型前必须做兼容检查。
7. **图谱查询需进一步加固**：NL2Cypher 应增加只读语法白名单、超时、LIMIT 强制和数据库只读权限。
8. **身份认证尚未接入主对话接口**：前端使用匿名本地 ID，API 直接接收 `user_id`；`jwt_utils` 尚未形成完整访问控制链路。
9. **临时文书下载缺少用户鉴权**：当前主要依靠高熵随机 ID 和短 TTL，生产环境应增加会话所有权校验。
10. **日志审计仍以文件为主**：知识检索记录到结构化日志，但没有独立审计表、查询面板和留存策略。
11. **附件解析有范围限制**：PDF 只抽取前 30 页且不做通用 OCR；扫描件需要转图片或接入 MinerU/OCR 服务。
12. **健康检查不等于数据就绪**：服务连通只能说明依赖可访问，不能证明集合已建、数据完整或模型凭据有效。

## 31. 推荐的后续建设优先级

### P0：上线前必须完成

- 重新启动基础设施并生成实时数据/索引盘点；
- 对权威来源完成版本有效性和法律内容审核；
- 给 API、文书下载和会话删除接入真实身份认证与所有权校验；
- 对 NL2Cypher 增加只读白名单和资源限制；
- 建立数据库—Milvus—Neo4j 数量与主键一致性检查；
- 使用生产密码、密钥管理和最小权限账号。

### P1：提升知识质量

- 建设 `evidence_basis_rules` 和独立 `proof_targets`，补齐“证明目标—评估维度—法律依据”；
- 给法条建立现行有效、修订、废止和历史版本关系；
- 完善电子数据、截图、录音、平台导出等专项证据规则；
- 建立专业文档库完整的上传、解析、切块、版本、权限和删除流程；
- 扩充地区化渠道并维护最近核验日期。

### P2：提升智能体可运营性

- 将检索审计、路由、耗时、降级、接地校验和用户反馈写入可查询的运营表；
- 增加模型调用成本、超时率和节点级成功率监控；
- 建立法条召回、类案相关性、证据覆盖和最终方案事实一致性的持续评测；
- 将 Professional/Exam Worker 从占位实现升级为独立、可测试的专项能力。

## 32. 一次完整案件请求的端到端示例

```text
用户：“公司拖欠我三个月工资，我有合同和工资流水。”
  1. 前端以 mode=case 发送 SSE 请求
  2. API 锁定当前会话为案件模式
  3. GuideState 建立 case_id
  4. 每轮紧急风险检查
  5. 抽取领域=劳动与社会保障、问题=拖欠劳动报酬
  6. 写入“欠薪三个月、持有劳动合同、持有工资流水”等原子事实
  7. 根据劳动目录检查劳动关系、离职状态、请求金额和证据目标
  8. 轻量检索追问所需法条与权威来源
  9. 生成 2—5 个高价值问题或证据清单
 10. 用户填写后更新事实和证据覆盖版本
 11. 执行法条、类案、图谱和渠道完整检索
 12. 形成争点图、法律依据包、逐争点适用分析和策略计划
 13. 做反方压力测试、草稿批判、修订和法条接地清洗
 14. 返回行动方案、证据缺口、渠道和下一步
 15. 保存 GuideState、咨询摘要和长期记忆
 16. 用户可继续补证，系统递增证据与方案版本并重新生成
 17. 用户可导出 Word 方案并下载相关官方空白模板
```
